# 新产品开发清单

这套框架以后做新产品，核心只做三层：

1. 用户前端
2. 业务 Skill
3. 页面/场景配置

底座层一般不用改：

- 用户与权限
- 运营后台
- 异步任务
- Worker
- 审批流
- 结果记录
- 模板中心
- 知识库
- 通用结果协议

---

## 1. 先定义产品

先把这 5 个问题写清楚：

1. 这个产品叫什么
2. 目标用户是谁
3. 有哪些页面
4. 每个页面解决什么问题
5. 每个页面背后调用哪个 Skill

建议先产出一个最小表：

```md
产品名：
目标用户：

页面1：
- 页面名：
- 作用：
- 输入：
- 输出：
- 对应 Skill：

页面2：
- 页面名：
- 作用：
- 输入：
- 输出：
- 对应 Skill：
```

---

## 2. 做前端页面

你主要做用户看到的东西：

- 页面布局
- 表单输入
- 上传区
- 参数选择
- 任务提交
- 结果展示
- 下载按钮
- 历史记录入口

每个页面要想清楚：

1. 用户输入什么
2. 调哪个接口
3. 用同步还是异步
4. 结果怎么展示
5. 如果有多步骤，是否要展示处理中状态

前端最常用的接口是：

- `POST /api/v1/workflows`
- `GET /api/v1/jobs/{job_id}`
- `GET /api/v1/results/{workflow_id}`
- `GET /api/v1/stream/{workflow_id}`

如果是长任务，默认走：

1. 提交任务
2. 拿到 `job_id`
3. 轮询 job 状态或接 SSE
4. 完成后拉结果

---

## 3. 做业务 Skill

每个新产品最关键的是 Skill。

你要做的是：

1. 定义 Skill 名称
2. 定义触发词
3. 定义 Skill 工作流
4. 实现每个工具步骤
5. 定义最终输出结构

一个 Skill 最少要明确：

- 输入需要什么
- 调哪些模型/工具
- 中间步骤有哪些
- 最终返回什么

强制建议：

1. 输出里一定要有 `summary`
2. 如果有文件产物，要带 `download_url`
3. 如果有结构化结果，要放在稳定字段里
4. 不要让前端依赖随意文本解析

---

## 4. 配页面和场景

如果一个页面只对应一个 Skill：

- 配单页
- 绑定这个 Skill

如果一个页面要串多个 Skill：

- 配 `scenario`
- 定义步骤顺序
- 必要时加条件、审批、fallback

你主要配这些：

- `project`
- `page`
- `skills`
- `scenario.steps`

场景层可以做的事：

- 多 Skill 串行
- 分组并行
- 条件执行
- 输入映射
- 输出映射
- fallback
- 审批节点

---

## 5. 配模板和知识库

如果这个产品要稳定输出，通常都要配这两样：

### 模板

适合放：

- 固定提示词
- 固定输出格式
- 行业话术
- 报告结构

### 知识库

适合放：

- 行业规则
- 产品资料
- SOP
- 专业文档
- 业务背景

原则：

1. 模板放“怎么说”
2. 知识库放“说什么”

---

## 6. 决定是否启用审批

下面这些场景建议开审批：

- 对外发文
- 合同/法务
- 报价/商业方案
- 高风险内容
- 重要客户交付

如果开审批：

- 在场景步骤里标 `approval_required`
- 后台审批中心会接住
- 审批通过后会继续执行

---

## 7. 设计结果页

结果页不要只显示一段文字。

建议固定包含：

1. 任务状态
2. 结果摘要
3. 结构化结果
4. 下载区
5. 历史记录
6. 错误提示

如果是复杂产品，再加：

- 分步骤结果
- 审批状态
- 使用知识库上下文
- 生成时间

---

## 8. 运营后台要配什么

一个新产品上线前，至少检查后台这几项：

1. 用户角色是否配置
2. 模板是否录入
3. 知识库是否录入
4. 审批流是否需要开启
5. 结果记录是否能看到
6. 作业执行是否正常

如果要判断这套后台本身是否已经“彻底落地”，看这里：

- `docs/ops-console-landing-log.md`

---

## 9. 上线前检查

每次上线前过这份清单：

1. 页面能正常打开
2. 提交任务能成功
3. 异步任务能完成
4. 结果页能正确展示
5. 下载链接能打开
6. 审批流能走通
7. 后台能看到作业和结果
8. Worker 挂掉后任务能恢复

---

## 10. 你以后每次真正要做的事

一句大白话：

你以后做一个新 AI 产品，通常只做这几件事：

1. 设计页面
2. 写页面前端
3. 写业务 Skill
4. 配页面场景
5. 录模板和知识库
6. 测试后上线

你一般不用再重做这些：

1. 队列
2. Worker
3. 审批系统
4. 用户权限
5. 结果协议
6. 运营后台骨架

---

## 11. 最小开发顺序

以后建议固定按这个顺序做：

1. 先定页面
2. 再定 Skill 输入输出
3. 再写 Skill
4. 再接前端提交
5. 再配场景
6. 再录模板/知识库
7. 最后测审批、异步、结果

---

## 12. 给 AI 工具的固定任务模板

以后你可以直接把下面这段话发给 AI 工具：

```md
基于星期五框架开发一个新产品。

产品信息：
- 产品名：
- 目标用户：
- 页面列表：
- 每个页面的功能：
- 每个页面绑定的 Skill：
- 是否需要多 Skill 场景：
- 是否需要审批：
- 是否需要模板：
- 是否需要知识库：

请按这套框架输出：
1. 前端页面方案
2. Skill 方案
3. project/page/scenario 配置方案
4. 需要录入的模板清单
5. 需要录入的知识库清单
6. 接口对接方案
7. 上线测试清单
```

---

## 13. 判断标准

如果一个需求不需要你改底座，只需要你改：

- 页面
- Skill
- 配置

那说明这个框架已经用对了。

如果你做一个新产品时，经常还要去改：

- 队列
- 审批系统
- 用户系统
- 结果协议
- 运营后台基础结构

那说明这个产品抽象还没收住，应该先回到底座层优化。
