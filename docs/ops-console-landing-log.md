# 运营后台彻底落地日志

更新时间：2026-05-14

最新进度补记：

- P0 已落地：权益流水、用户运营动作、任务重试/退款、操作审计
- P1 已落地：优惠券、试用赠送、客服工单、用户申诉、支付回调、风险案件、配置发布/回滚
- P1 仍待补：更完整的自动支付回调接入、真实文件级配置回滚

## 1. 目标定位

这套后台的目标不是开发者控制台，也不是多项目平台。

它的准确定位是：

- 单个独立 AI 应用的运营后台
- 面向 C 端产品经营
- 一个应用一套后台
- 围绕用户、支付、任务、内容、模型、增长、客服、风控来运营

彻底落地的判断标准不是“页面很多”，而是：

- 运营每天需要做的事，基本都能在后台完成
- 产品配置核心能力时，不需要改代码
- 支付、权益、任务、结果之间是闭环的
- 出问题时，客服和运营有处理动作，不只是看状态

---

## 2. 什么叫彻底落地

如果一个后台彻底落地，至少要满足下面 6 条：

1. 用户从注册到付费到使用到留存，后台有完整经营视图
2. 套餐、订单、权益、扣费、退款、补偿，后台能闭环处理
3. 任务从提交到排队到结果到异常，后台能查看也能干预
4. 模板、知识库、页面能力、模型策略，后台能配置和发布
5. 增长活动、邀请码、优惠券、转化数据，后台能配置和追踪
6. 客诉、风控、申诉、审核、操作审计，后台能承接

只做到“能看数据”，不算彻底落地。

只做到“能配对象”，但不能处理异常，也不算彻底落地。

---

## 3. 当前状态结论

当前这版已经落地的是主干，不是全量。

已落地主干：

- 用户基础对象
- 套餐 / 订单 / 用户权益
- 已支付订单发权益
- 页面级按额度收费
- 任务执行扣点与失败退款
- 工作流 / 异步作业 / 审批 / 结果记录
- Prompt 模板 / 知识库 CRUD

还没彻底落地的部分：

- 用户运营动作不完整
- 支付链路不完整
- 任务运营动作不完整
- 增长运营基本未落地
- 客服与风控未形成闭环
- 配置发布、版本和审计不完整

结论：

- 当前完成度更接近“运营后台底座 + 核心经营主链路”
- 距离“可长期支撑大多数 C 端 AI 应用运营”的完整后台，还有一轮系统化补全

---

## 4. 必须落地的模块清单

下面这些不是可选增强，而是要把后台做成真正运营后台时必须落地的对象。

### 4.1 用户运营

必须有：

- 用户基础资料：ID、昵称、手机号/邮箱、注册来源、注册时间
- 账号状态：active / disabled / banned / white_listed
- 用户标签：来源、渠道、偏好、风险等级、价值等级
- 用户分层：新用户、活跃用户、沉默用户、付费用户、高价值用户
- 最近行为：最近登录、最近任务、最近支付、最近投诉
- 用户权益摘要：当前套餐、订阅状态、额度余额、到期时间

必须有的动作：

- 封禁 / 解封
- 加白 / 去白
- 手动补偿额度
- 手动改订阅状态
- 记录运营备注

必须有的记录：

- 用户操作日志
- 补偿日志
- 封禁原因
- 权益调整历史

### 4.2 支付与权益

必须有：

- 套餐中心：订阅、点数包、单次包、试用包
- 订单中心：pending / paid / failed / refunded / closed
- 权益中心：订阅状态、额度余额、累计发放、累计消耗
- 权益流水：每次发放、扣减、退款、补偿都要有明细

必须补全的链路：

- 支付回调
- 支付成功发权益
- 退款回收或补偿权益
- 试用发放
- 优惠券 / 活动券
- 到期处理
- 续费处理

后台必须能做的动作：

- 手动创建订单
- 手动标记到账
- 手动退款
- 手动补发权益
- 查单和对账

### 4.3 任务与交付

必须有：

- 工作流列表
- 异步作业列表
- 任务状态流转
- 最终结果记录
- 产物下载
- 审批节点记录

必须补全的运营动作：

- 取消任务
- 重试任务
- 重新投递
- 补发结果
- 标记异常
- 异常任务补偿
- 付费任务失败退款联动

必须补全的经营字段：

- 任务来源页面
- 任务计费类型
- 本次消耗额度
- 是否退款
- 用户是否已收到结果

### 4.4 功能与内容配置

必须有：

- Prompt 模板中心
- 知识库中心
- 页面配置
- 场景配置
- 模型策略配置

必须补全：

- 配置发布状态：draft / published / archived
- 配置版本号
- 最近发布人
- 变更说明
- 回滚能力

后台必须能做的动作：

- 编辑模板并生效
- 编辑知识库并生效
- 调整页面收费配置
- 调整页面审批配置
- 调整页面调用的 Skill / 场景顺序

### 4.5 模型与成本

必须有：

- 提供商状态
- 模型状态
- 熔断状态
- 成本统计
- 按模型成本拆分
- 按页面 / 场景成本拆分

必须补全：

- 页面级模型策略
- 复杂度路由策略
- 成本上限
- 降级策略
- 高成本报警

后台必须能做的动作：

- 启停模型
- 调整默认模型
- 调整 fallback
- 控制高成本页面的模型等级

### 4.6 增长运营

这是当前缺口最大的一块，不能再只留结构位。

必须有：

- 邀请码 / 邀请关系
- 渠道来源
- 活动配置
- 优惠券发放
- 新手引导开关
- 转化漏斗

必须补全的对象：

- campaign
- coupon
- invite_code
- referral_record
- channel_attribution
- experiment / ab_test

后台必须能做的动作：

- 创建活动
- 生成邀请码
- 给某类用户发券
- 查看转化数据
- 开关新手引导
- 配置首单优惠 / 首次赠送额度

### 4.7 客服与风控

必须有：

- 审批中心
- 客诉 / 工单
- 用户申诉
- 风险标记
- 审核队列

必须补全的对象：

- support_ticket
- appeal_record
- risk_case
- moderation_queue
- audit_log

后台必须能做的动作：

- 受理工单
- 处理申诉
- 审批通过 / 驳回
- 标记高风险用户
- 冻结账号
- 冻结权益

### 4.8 系统配置与审计

必须有：

- 配置快照
- 配置变更记录
- 后台操作日志
- 审批日志
- 支付日志
- 退款日志

必须补全：

- 谁在什么时候改了什么
- 改前值 / 改后值
- 配置发布记录
- 敏感操作二次确认

## 5. 当前版本缺口表

### 已基本落地

- 用户基础台账
- 套餐 / 订单 / 权益对象
- 订单到账发权益
- 页面收费校验
- 扣点 / 失败退款
- 任务 / 审批 / 结果中心
- 模板 / 知识库中心

### 半落地

- 用户运营：能看，不能完整运营
- 模型与成本：能看，不能完整策略化运营
- 系统设置：已接模板/知识库快照发布与回滚，但还不是全局配置发布系统
- 客服与风控：已接工单、申诉、风险案件，但还没有自动化审核规则

### 未落地或明显不足

- 增长运营的归因、活动、实验能力
- 邀请码 / 渠道归因
- 自动化支付回调与对账
- 续费 / 到期 / 优惠券复杂规则
- 操作审计

## 6. 彻底落地的优先级顺序

不要继续横向加页面，应该按经营闭环补。

### P0：必须先补

1. 权益流水
2. 退款与补偿闭环
3. 用户运营动作：封禁、加白、补偿、备注历史
4. 任务运营动作：重试、取消、补发、异常退款
5. 操作审计日志

### P1：第二轮补

1. 支付回调
2. 试用与赠送
3. 优惠券
4. 工单 / 申诉
5. 风险标记与审核队列
6. 配置发布 / 版本 / 回滚

### P2：第三轮补

1. 邀请码
2. 渠道归因
3. 增长活动
4. 漏斗与转化统计
5. A/B 实验
6. 页面级模型运营策略

## 7. 落地验收标准

后台什么时候才算真正可上线运营，用下面这份验收。

### 用户

- 运营能找到任意用户
- 能看用户当前套餐、余额、最近任务、最近支付
- 能封禁、加白、补偿，并留下日志

### 支付

- 套餐能配置
- 订单能创建、查询、到账、退款
- 支付成功后权益会发放
- 退款后权益处理规则明确
- 每次权益变更都有流水

### 任务

- 能看任务状态、结果、产物
- 能取消、重试、补发
- 收费任务能看到本次扣点和退款状态

### 配置

- 模板、知识库、页面收费、审批配置都能改
- 改完能发布
- 发布后能回滚

### 增长

- 能发券
- 能做活动
- 能识别渠道
- 能看转化

### 客服与风控

- 客诉有工单承接
- 申诉有处理流
- 高风险用户可冻结
- 审批和操作都有日志

---

## 8. 对当前底座的最终要求

以后基于这套底座做大多数 C 端 AI 应用时，应该满足：

- 做新项目时，不再重做运营后台
- 只需要补业务字段和页面配置
- 大部分经营动作直接复用底座后台

如果未来做新应用时，还需要频繁回到底座补这些，说明后台还没有真正收口：

- 用户补偿
- 支付退款
- 权益流水
- 任务补发
- 工单申诉
- 活动发券
- 配置回滚
- 操作审计

---

## 9. 下一阶段实施原则

从这一版开始，运营后台后续建设只遵守 3 条原则：

1. 不再做开发者炫技型页面
2. 只做运营每天真的会用的对象和动作
3. 所有页面都优先追求“可执行闭环”，不是“展示完整”
